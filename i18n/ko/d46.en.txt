A room is mostly air, and the interesting part of a map is the thin layer around surfaces. A plain 3D array pays for every voxel of the bounding box. Hash tables and trees pay only for the voxels that hold something, in exchange for a more complicated lookup. Which one to use, and how to push thousands of beams per scan into it, decides whether a mapping system runs in real time.

1. The dense array and its bill
@@ 14
The simplest storage is one array, plus a function from a position to an array index. <span class="src">§5.3.3.1 · p. 132</span> For a grid with origin \((x_0, y_0, z_0)\), cell size \(\Delta\), and \(N_x \times N_y \times N_z\) cells, a point \((x, y, z)\) lies in the cell
@@ 15
where \(\lfloor\cdot\rfloor\) rounds down and \(n\) is the position in the array. Example: origin \((-10, -10, 0)\), \(\Delta = 0.25\) m, \(N_x = N_y = 80\). The point \((2.6, -3.1, 1.3)\) gives \(i = \lfloor 50.4 \rfloor = 50\), \(j = \lfloor 27.6 \rfloor = 27\), \(k = \lfloor 5.2 \rfloor = 5\), and \(n = 50 + 80 \times (27 + 80 \times 5) = 34{,}210\). A lookup is a handful of arithmetic operations, which is why this layout is fast.
@@ 16
The cost is memory. Map a 100 m × 100 m × 10 m building at 5 cm: \(2000 \times 2000 \times 200 = 8 \times 10^{8}\) voxels. At 4 bytes each that is 3.2 GB. Halving the voxel size to 2.5 cm multiplies the count by \(2^3 = 8\), to 25.6 GB. Memory grows linearly with the mapped volume and with the cube of the resolution. <span class="src">§5.4.4.4 · p. 140</span> And when the robot drives out of the box, the whole array has to be copied into a larger one. <span class="src">§5.3.3.1 · p. 132</span>

2. Hash tables and voxel blocks
@@ 18
A hash table keeps the fast lookup and drops the bounding box. Cut the map into pieces with integer coordinates (single voxels, or <strong>voxel blocks</strong> of, say, 8 × 8 × 8 voxels), and store only the pieces that contain data in a table. <span class="src">§5.3.3.2 · p. 133</span>
@@ 19
Filling the gap: what a hash table does
@@ 20
A <strong>hash function</strong> turns a key, here a block coordinate, into a slot number in a table of fixed size. To find block \((i, j)\) you compute its slot and look there; no search through the map is needed, so the cost does not depend on how large the map is. That is the \(O(1)\) of the book. Two different keys can land in the same slot, a <strong>collision</strong>. The table then stores both, for example in a short list hanging off the slot, and compares keys to pick the right one. A good hash function spreads neighbouring blocks over the table so that collisions stay rare.
@@ 21
The figure uses the toy function \(\text{slot} = (7i + 13j) \bmod 16\). Block \((2, 2)\) goes to \((14 + 26) \bmod 16 = 8\).

Voxel-block hashing in 2D. Only blocks that the surface passes through exist in memory, and each is found through its slot. Inside a block the voxels are a small dense array, so the arithmetic of section 1 still applies there.

The block size is a trade. Small blocks follow the surface closely and waste few empty voxels, but there are many of them, which makes the table large and slow to insert into. Large blocks are the reverse. <span class="src">§5.3.3.2 · p. 133; §5.4.4.2 · p. 139</span>

3. Trees
@@ 29
An <strong>octree</strong> covers space with one cube, the root <strong>octant</strong>, given by a centre \(\mathbf{c}\) and an extent \(e\). Any octant can be split into eight children of extent \(e/2\), and only the children that contain data are created. <span class="src">§5.3.3.3 · pp. 133–134</span> After \(d\) splits the cell size is \(e/2^d\): a 102.4 m root reaches 10 cm cells at depth 10. If new data falls outside the root, a larger root is put on top and the old root becomes one of its children.
@@ 30
What a tree adds over a hash table is hierarchy. Large uniform regions are stored as one big node, coarse versions of the map come for free, and searches such as "nearest neighbour" can discard whole branches. What it costs is that reaching a leaf takes one step per level, and that the parent-child links themselves use memory. <span class="src">§5.3.3.3 · p. 134</span>
@@ 31
Try it: a quadtree, the 2D octree, on this week's room. Set the depth to 1, then raise it one step at a time and compare how the two cell counts grow.
@@ 32
Notice that up to depth 3 the tree saves almost nothing: the squares are so large that nearly every one could touch a surface. From depth 5 on, each extra level about doubles the leaves (833, 1637, 3323) while the dense grid quadruples. At depth 7 the tree holds 10% of the cells of the grid.
@@ 33
The reason is geometric. At depth \(d\) the cells have size \(e/2^d\). A curve of length \(L\) passes through roughly \(L \cdot 2^d / e\) of them, a number that doubles per level, while the full grid has \(4^d\) cells. In 3D a surface crosses a number of cells that grows like \(4^d\), against \(8^d\) for the full grid. Sparse structures store the surface, not the volume.
@@ 34
<strong>Hybrid</strong> structures combine the two. Hashed voxel blocks keep a dense array inside each block, which is simple and suits GPUs. The VDB structure hashes blocks and puts a small tree of fixed height inside each, so lookups take constant time and the map still has several resolutions. <span class="src">§5.3.3.4 · pp. 134–135</span>

@@ 44

@@ 47
Delaunay triangulation of the points, keeping the triangles on the surface.
@@ 48

Meshes, through an implicit surface
@@ 50
First fit an implicit surface (radial basis functions, moving least squares, Poisson reconstruction, or a TSDF), then extract its zero set.
@@ 51

5. Voxel maps in practice
@@ 53
<strong>What to estimate.</strong> Occupancy has the better recall, so few obstacles are missed, which suits collision avoidance. TSDFs give better surfaces where the world is smooth and lose thin objects (Day 2). A TSDF overestimates distances, which is unsafe for a planner, so systems such as voxblox compute a true ESDF from the TSDF with a wavefront (brushfire) algorithm, and FIESTA computes one from an occupancy map. <span class="src">§5.4.4.1 · p. 138</span>

Filling the gap: which voxels does a ray cross?
@@ 69
Ray tracing needs the exact list of cells between two points. Sampling the ray at small steps can skip a cell that the ray only clips. The standard exact method, due to Amanatides and Woo, steps from cell to cell. For a ray \(\mathbf{o} + t\,\mathbf{d}\) with unit direction \(\mathbf{d}\), keep for each axis the ray length \(t\) at which the next cell boundary on that axis is crossed. The smallest of these tells which boundary comes first.
@@ 70
Each loop turn moves to exactly one neighbouring cell with two additions and one comparison per axis, and no cell is skipped or visited twice.
@@ 71
<strong>How to scale.</strong> Octomap stores occupancy in an octree and merges children whose values agree with their parent, so open space collapses into a few large nodes. It still integrates every beam at the finest resolution, so the update cost stays cubic. Later systems also lower the update resolution with distance, since beams spread out, and skip updates that would change nothing; wavemap does this on a wavelet encoding of the map, which stores differences between resolution levels. <span class="src">§5.4.4.4 · pp. 140–141</span>

@@ 79
i = ⌊12.6 / 0.25⌋ = 50 and j = ⌊6.9 / 0.25⌋ = 27, so n = 50 + 80 × 27 = 2210. Swapping i and j gives 4027; rounding 27.6 up instead of down gives 2290.

Q3. An octree's root octant has an extent of 51.2 m and its finest leaves are 10 cm. How many levels does a lookup descend?
@@ 81
Each level halves the extent: 51.2 / 2⁹ = 0.1 m, so 9 levels. The lookup time grows with this height, which is the cost of a pure tree.

Q4. Why do GPU mapping systems prefer projection-based integration?
@@ 83
It needs only the sensor position, not its orientation
@@ 84
It loops over voxels, so each voxel is written by one thread and no two updates collide
@@ 85
It works best on unorganized point clouds
@@ 86
It never touches free-space voxels
@@ 87
Looping over the map gives every voxel exactly one update per scan, with no race conditions and a predictable memory pattern. The price is that it needs the full sensor pose and projection model, which is the opposite of the first option.
@@ 88
A dense array gives the fastest lookup, \(n = i + N_x(j + N_y k)\), and the largest memory bill: linear in volume, cubic in resolution.
@@ 89
A hash table stores only the blocks that hold data and finds each in constant time. Voxel-block hashing keeps a small dense array in each block.
@@ 90
An octree splits space only where there is data and gives several resolutions, at the cost of a lookup that takes one step per level. Sparse structures grow with the surface area, not the volume.
@@ 91
Point and surfel maps are thinned with grids or trees. Meshes are built directly from points or, more robustly, from an implicit surface.
@@ 92
Ray-tracing integrators loop over beams and need only the sensor position. Projection integrators loop over voxels, need the full sensor model, and parallelize well.
