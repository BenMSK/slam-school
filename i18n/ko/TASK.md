# Translating one week of SLAM School into Korean

SLAM School (`index.html`) is a 24-week English course that accompanies the *SLAM Handbook*. Its Korean page `ko.html`
is generated by `tools/i18n.py` from `index.html` plus the translations in `i18n/ko/`. You translate ONE week.
Project root: `C:\Users\msk93\Documents\Apps\SLAM`. Run every command from there.

Read `i18n/ko/STYLE.md` first and follow it exactly. Its central rule: prose in Korean, every SLAM / math / ML term of
art and every proper noun in English, exactly as the English lesson writes it.

## 1. Your files (write only these)

Week W has six day chunks: day k is `d{(W-1)*6+k}` (Week 5 → d25…d30; Week 13 → d73…d78).

| You write | From |
|---|---|
| `i18n/ko/dN.ko.txt` for each of your six days | `i18n/ko/dN.en.txt` (do not edit the `.en.txt`) |
| `i18n/ko/js.wNN.txt` (NN = two-digit week) | the week's widget code: `src/wNN/*.js` |

Do not touch any other file: not `index.html`, `src/`, `tools/`, `STYLE.md`, `common.*`, `ui.*`, `js.ui.txt`, or other
weeks' files. `common` (headings repeated across the course, such as "Today's big idea") and `ui` (header, overview,
the day/week labels and buttons made by the app script) are translated by the main session.

## 2. The text files

`dN.en.txt` is a list of numbered units. Each unit starts with a header line `@@ 12` (or `@@ 12 attr`) followed by the
HTML of one text block: a paragraph, a heading, a list item, a table cell, a quiz option, an SVG label, or an attribute
value. Long units are wrapped over several lines; that is only for display.

`dN.ko.txt` must have exactly the same header lines, in the same order, each followed by the Korean for that unit:

```
@@ 1
흔한 실수
@@ 2
=
@@ 3 attr
3개의 pose와 2개의 landmark를 가진 factor graph
```

- `=` alone means "keep the English exactly" (a term, a name, a number, a formula-only label).
- Keep every tag of the unit, character for character (you may move a tag with its words). Keep every formula
  `\( … \)` / `\[ … \]` character for character; only words inside `\text{…}` may change. Keep every page chip
  `<span class="src">…</span>` as it is.
- Units are deduplicated per day: the same block appears once. Blocks that appear in 3+ days are in `common` and
  are not in your files.
- Write the whole file. For a long day, write it in two or three parts (Write the first part, then Edit to append),
  but never leave a unit out.

## 3. The widget strings (`js.wNN.txt`)

The widgets are JavaScript in `src/wNN/*.js` (the same code sits in `index.html`). Their visible English text lives in
string literals: titles (`h("div",{class:"vt"},"…")`), descriptions, slider labels (`range("…",…)`), button labels,
legend items, stat tiles (`stat("…","…","…")`), axis labels, `aria-label`s, captions and messages built with `+` or
template literals. Translate them with snippet pairs:

```
@@ w05
h("div",{class:"vt"},"Fit a trajectory with a B-spline")
==
h("div",{class:"vt"},"B-spline으로 trajectory 맞추기")
@@ w05
"Knot spacing"
==
"knot 간격"
@@ w05
stat("Mean position error",
==
stat("평균 위치 오차",
```

- The header is always `@@ wNN` (your week). A pair replaces every occurrence of the English snippet inside your week's
  code, and nowhere else. Longer snippets are applied first.
- The English snippet must be copied exactly from the source, including quotes and spacing; the build reports any
  snippet it cannot find. Include enough context (the quotes, or the function name) that a short word does not hit
  code: never a pair like `"x"` or `"on"` that could match a property name, a class name, an event name, an id, or a
  value the code compares against. Never translate strings the code uses as keys, CSS classes, colours, event names,
  `select` option values, or values tested with `===`.
- Translate only text inside string or template literals. Never change code, numbers, `toFixed` calls, units, or
  variable names. Keep `+` concatenations working: if a sentence is split around a number, translate each piece so
  the joined result reads as Korean (word order may need the pieces rearranged; then replace the whole expression).
- Terms and symbols stay in English (STYLE.md). Keep labels short: Hangul is about twice as wide as Latin letters.
- Strings the shared app code makes (week/day labels, "Mark … done", "← Back", "Next →" of the stepper) are handled
  in `js.ui.txt`; leave them.

## 4. Check your work (required)

```
python tools/i18n.py check wNN
node tools/build.js --week W --nosmoke
python tools/i18n.py build wNN build/ko_wNN.html --src build/wNN.html
python tools/review.py dN --html build/ko_wNN.html
```

1. `check wNN` must print `0 findings` for all six days. A "numbers in the English but not in the Korean" finding is
   acceptable only when you turned a number word into Korean on purpose; every other finding is a real error.
2. The preview build must print `untranslated units:` with none of your days listed (ui misses are expected),
   `script errors: 0`, `htmlcheck: errors: 0` and `smoke: … 0 errors`.
3. Run `review.py` for each of your six days (it audits SVG labels and screenshots every figure and widget of that
   day from the Korean preview). Read the PNG of every widget and of the figures with the most text, and fix Korean
   labels that overflow, overlap, or get cut off (shorten them, or keep the English with `=`).
4. Re-run steps 1 and 2 after your last edit.

If you write helper scripts, put them in the session scratch folder with a `koNN_` file-name prefix (other agents
share that folder).

## 5. Final report (under 150 words)

The six days done, the number of units translated and kept (`=`), the number of widget pairs, the last results of
`check` and the preview build, and anything you could not translate cleanly or think is wrong in the English.
