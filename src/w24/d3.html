Today's big idea

The algorithms of Spatial AI already have graph structure: the map is a graph of features, the real-time loop is a fixed processing graph, and an image is a grid of pixels. The chapter's design gives each graph hardware of the same shape, so that most computation happens where its data already sits, and connects the pieces with as few bits as possible.

1. The design in one picture

The chapter considers one device working with on-board resources only, since that works anywhere. §18.5 · pp. 532–533 Its claim is that long-term efficiency comes from matching the graph structures of the algorithms to the physical layout of the hardware. That argues for pushing work out toward the sensors. Yet most of the computation stays central, for one reason: the world model. Every new piece of data is in the end compared with it, and then either updates it or is discarded. §18.5 · p. 533 Figure 18.1 draws the result as a "Spatial AI brain". §18.5.1 · p. 534

The last column is this app's reading; the book gives no rates. The central unit is not a CPU with RAM. A CPU reaches any memory cell at about the same cost, but spatial data is local, and so is the work of adding to it. The design asks for storage and processing combined in one graph-shaped unit, like Graphcore's IPU, where a program is compiled into a layout of operations, data, and communication channels over the cores. §18.5.1 · p. 534

2. The map store: a graph that maintains itself

A "feature" here is any abstraction of a scene entity, from a point to an object. Each can be measured only from some region of camera positions, so as the camera moves, features come into view in overlapping groups. Features measured at the same time become strongly correlated through the uncertain camera state, features a short motion apart less so, and distant ones only weakly. Join strongly correlated features, cut edges below a threshold, and a sparse graph of nearby features is left. §18.5.1.1 · p. 535

Filling the gap: "correlated through the camera state", with numbers

In one dimension, let the camera's position have error variance \(\sigma_x^2\). It measures two landmarks, each with independent noise of variance \(\sigma_z^2\), and places them at \(\hat{l}_i = \hat{x} + z_i\). Each landmark's error is the camera's error plus its own noise:

\[ \hat{l}_i - l_i = (\hat{x} - x) + n_i, \qquad \operatorname{var}(\hat{l}_i) = \sigma_x^2 + \sigma_z^2, \qquad \cov(\hat{l}_1,\hat{l}_2) = \sigma_x^2 . \]

The shared term \(\hat{x}-x\) is the covariance, so the correlation is \(\rho = \sigma_x^2/(\sigma_x^2 + \sigma_z^2)\). With \(\sigma_x = 0.1\) and \(\sigma_z = 0.02\): \(\rho = 0.01/0.0104 = 0.96\). The camera does not know where it is, but it knows well where the landmarks are relative to each other.

Now let the camera take \(n\) odometry steps, each adding error variance \(\sigma_o^2\), before it measures landmark 2. Then \(\operatorname{var}(\hat{l}_2) = \sigma_x^2 + n\sigma_o^2 + \sigma_z^2\) while the shared part is still \(\sigma_x^2\). With \(n\sigma_o^2 = 0.09\):

\[ \rho = \frac{0.01}{\sqrt{0.0104 \times 0.1004}} = \frac{0.01}{0.0323} = 0.31 . \]

More motion between two observations means a weaker edge. In the language of Week 3 · Day 3: eliminating a pose links every pair of features seen from it, so the feature graph follows co-visibility.

A pose graph has the same shape with poses in place of features, and the chapter sees no fundamental difference. Its conclusion: represent space by a graph of features, linked in multi-scale patterns that follow camera motion, and able to generate dense predictions. §18.5.1.1 · pp. 535–536 That graph is laid out across many cores whose connections mirror it. Much of large-scale SLAM can then run inside the store as maintenance: clustering features and segmenting objects, detecting loop closures, optimizing after them, smoothing the map, and discovering new semantic categories. Smoothing and segmentation act on each part separately; global optimization can use message passing (tomorrow). Memory sets a deadline: an IPU has about 1 MB per tile, about 1 GB over 1000 tiles, so dense data should be abstracted quickly toward a compact object-level form. §18.5.1.1 · p. 536

3. The real-time loop, and the problem of a moving window

The chapter expects the tightest loop to look like today's dense SLAM (Week 12 · Day 5): model the world in enough generative detail that every new pixel can be compared with a prediction. Its elements are labeling (pixels to features, usually by a network), rendering (a dense predicted image from the map), tracking (aligning prediction and image, finding outliers and independent motion), fusion (writing geometry and labels back), and self-supervised learning. Rendering reads the map and fusion writes it. §18.5.2 · p. 537

These are fixed blocks of massively parallel work and suit a fixed processing graph. The hard part is the link to the map: the part in view changes constantly with motion, so no fixed data path leads to "the relevant memory". The proposed answer is a set of interface nodes, communication specialists wired to the loop on one side and to many sites of the map graph on the other. If the store has a small-world topology, where any two nodes are a few hops apart, they can copy any needed part of the map in a few operations. §18.5.2 · pp. 537–538

4. Processing close to the image plane

Pixels form a grid, and neighbouring pixels usually see the same object, so a graph linking each pixel to its four neighbours underlies smoothing in dense matching and optical flow. §18.5.3 · p. 538 A chip like SCAMP5 can do such bottom-up work itself. Optical flow fits well: its parallel form alternates a per-pixel data step with smoothing between neighbours. §18.5.3 · pp. 538–539

SLAM tracking is harder because it wants one set of global motion parameters. On ordinary hardware, dense tracking alternates a parallel step (an error at every pixel) with a reduction step (sum all errors, update the parameters). The reduction is a global regularizer, and a grid of pixel processors cannot do it without sending everything to one place. The chapter's way out is to give up guaranteed global consistency and converge toward it: each pixel keeps its own estimate of the global parameters and shares it with its neighbours every iteration. After enough rounds any pixel can be asked for a usable answer, and longer links, or a small-world pattern, would speed this up. §18.5.3 · p. 539

Try it: 64 pixels each hold a local estimate of one global number. The Rounds slider runs neighbour-to-neighbour averaging; the second slider adds long links.

Notice that with grid links only, the numbers smooth out locally within a few rounds but a left-to-right slope survives: after 20 rounds the spread is still 1.34, and it takes 100 rounds before every pixel is within 0.05 of the global mean, 2.045. Add 16 long-range links: the longest shortest path drops from 14 hops to 7, and the same agreement takes 32 rounds. No pixel ever computed a global sum.

Filling the gap: why local averaging finds the global mean

The book expects convergence and gives no rule. The simplest one: give every link \((i,j)\) a weight \(w_{ij} = w_{ji}\), and in each round let every pixel move toward each neighbour,

\[ x_i \leftarrow x_i + \sum_{j \in \text{nbrs}(i)} w_{ij}\,(x_j - x_i), \qquad w_{ij} = \frac{1}{1 + \max(d_i, d_j)}, \]

where \(d_i\) is the number of neighbours of pixel \(i\).

The sum never changes. Link \((i,j)\) adds \(w_{ij}(x_j - x_i)\) to pixel \(i\) and the opposite to pixel \(j\).

The only resting state is agreement. With these weights each new value is a weighted average of a pixel and its neighbours, so the largest value can only fall and the smallest only rise until all are equal. The sum is fixed, so the common value is the mean of the starting values, which is what the reduction step would have computed.

Check on three pixels in a row holding 1, 2, 6. The degrees are 1, 2, 1, so both links have weight \(1/3\). One round gives \(1 + \tfrac13(2-1) = 1.33\), \(2 + \tfrac13(1-2) + \tfrac13(6-2) = 3\), and \(6 + \tfrac13(2-6) = 4.67\). The sum is still 9, and the values head for 3.

Information moves one hop per round, so the shape of the graph sets the speed. Averaging treats all pixels as equally reliable; Gaussian belief propagation, tomorrow, passes uncertainty along with the estimate.

The flow need not be one-way. If the main processor sends its prediction to the camera, the camera needs to report only what differs. An event camera reports a pixel when its brightness changes, which amounts to predicting that nothing changes; a model-based event camera would report a pixel when it departs from the model's prediction. §18.5.1 · p. 535; §18.5.3 · p. 540 The aim throughout is fewer bits on the link, and with them less communication power. §18.4.2 · p. 532

Check yourself

Q1. Three pixels in a row hold 0, 3, 9 and average with the weights from "Filling the gap". What does the middle pixel hold after one round?

Both links have weight 1/3. The middle pixel becomes 3 + (0 − 3)/3 + (9 − 3)/3 = 4. The ends become 1 and 7, and the sum stays 12.

Q2. Two landmarks are measured from the same camera pose. The pose error variance is 0.04 and each measurement has noise variance 0.01. What is the correlation between the two landmark estimates?

ρ = σx² / (σx² + σz²) = 0.04 / 0.05 = 0.8. The shared camera error is the covariance.

Q3. Which job does the chapter place inside the map store and not in the real-time loop?

Loop-closure detection and optimization, smoothing, and clustering are maintenance the store performs on itself. Rendering, tracking, and fusion connect the live image to the map.

Q4. Why does the design need interface nodes between the real-time loop and the map store?

Motion changes which map nodes the loop needs. Interface nodes linked to many sites of a small-world map graph can fetch any part in a few hops.

Recap

  1. The design matches hardware to the graphs in the algorithms, but keeps most computation central because all data is compared with one world model.
  2. The map is a sparse graph: features seen together are strongly correlated through the camera state. The store holds it across many cores and maintains it in place.
  3. The real-time loop labels, renders, tracks, and fuses. Interface nodes and a small-world map topology connect it to a map whose relevant part keeps moving.
  4. Near the image plane a global estimate can be reached by local message passing, at a cost in rounds that depends on the graph. Two-way links let a sensor send only what the model did not predict.
