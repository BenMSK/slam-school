Today's big idea

A room is mostly air, and the interesting part of a map is the thin layer around surfaces. A plain 3D array pays for every voxel of the bounding box. Hash tables and trees pay only for the voxels that hold something, in exchange for a more complicated lookup. Which one to use, and how to push thousands of beams per scan into it, decides whether a mapping system runs in real time.

1. The dense array and its bill

The simplest storage is one array, plus a function from a position to an array index. §5.3.3.1 · p. 132 For a grid with origin \((x_0, y_0, z_0)\), cell size \(\Delta\), and \(N_x \times N_y \times N_z\) cells, a point \((x, y, z)\) lies in the cell

\[ i = \left\lfloor \frac{x - x_0}{\Delta} \right\rfloor, \quad j = \left\lfloor \frac{y - y_0}{\Delta} \right\rfloor, \quad k = \left\lfloor \frac{z - z_0}{\Delta} \right\rfloor, \qquad n = i + N_x\,(j + N_y\,k), \]

where \(\lfloor\cdot\rfloor\) rounds down and \(n\) is the position in the array. Example: origin \((-10, -10, 0)\), \(\Delta = 0.25\) m, \(N_x = N_y = 80\). The point \((2.6, -3.1, 1.3)\) gives \(i = \lfloor 50.4 \rfloor = 50\), \(j = \lfloor 27.6 \rfloor = 27\), \(k = \lfloor 5.2 \rfloor = 5\), and \(n = 50 + 80 \times (27 + 80 \times 5) = 34{,}210\). A lookup is a handful of arithmetic operations, which is why this layout is fast.

The cost is memory. Map a 100 m × 100 m × 10 m building at 5 cm: \(2000 \times 2000 \times 200 = 8 \times 10^{8}\) voxels. At 4 bytes each that is 3.2 GB. Halving the voxel size to 2.5 cm multiplies the count by \(2^3 = 8\), to 25.6 GB. Memory grows linearly with the mapped volume and with the cube of the resolution. §5.4.4.4 · p. 140 And when the robot drives out of the box, the whole array has to be copied into a larger one. §5.3.3.1 · p. 132

2. Hash tables and voxel blocks

A hash table keeps the fast lookup and drops the bounding box. Cut the map into pieces with integer coordinates (single voxels, or voxel blocks of, say, 8 × 8 × 8 voxels), and store only the pieces that contain data in a table. §5.3.3.2 · p. 133

Filling the gap: what a hash table does

A hash function turns a key, here a block coordinate, into a slot number in a table of fixed size. To find block \((i, j)\) you compute its slot and look there; no search through the map is needed, so the cost does not depend on how large the map is. That is the \(O(1)\) of the book. Two different keys can land in the same slot, a collision. The table then stores both, for example in a short list hanging off the slot, and compares keys to pick the right one. A good hash function spreads neighbouring blocks over the table so that collisions stay rare.

The figure uses the toy function \(\text{slot} = (7i + 13j) \bmod 16\). Block \((2, 2)\) goes to \((14 + 26) \bmod 16 = 8\).

The block size is a trade. Small blocks follow the surface closely and waste few empty voxels, but there are many of them, which makes the table large and slow to insert into. Large blocks are the reverse. §5.3.3.2 · p. 133; §5.4.4.2 · p. 139

3. Trees

An octree covers space with one cube, the root octant, given by a centre \(\mathbf{c}\) and an extent \(e\). Any octant can be split into eight children of extent \(e/2\), and only the children that contain data are created. §5.3.3.3 · pp. 133–134 After \(d\) splits the cell size is \(e/2^d\): a 102.4 m root reaches 10 cm cells at depth 10. If new data falls outside the root, a larger root is put on top and the old root becomes one of its children.

What a tree adds over a hash table is hierarchy. Large uniform regions are stored as one big node, coarse versions of the map come for free, and searches such as "nearest neighbour" can discard whole branches. What it costs is that reaching a leaf takes one step per level, and that the parent-child links themselves use memory. §5.3.3.3 · p. 134

Try it: a quadtree, the 2D octree, on this week's room. Set the depth to 1, then raise it one step at a time and compare how the two cell counts grow.

Notice that up to depth 3 the tree saves almost nothing: the squares are so large that nearly every one could touch a surface. From depth 5 on, each extra level about doubles the leaves (833, 1637, 3323) while the dense grid quadruples. At depth 7 the tree holds 10% of the cells of the grid.

The reason is geometric. At depth \(d\) the cells have size \(e/2^d\). A curve of length \(L\) passes through roughly \(L \cdot 2^d / e\) of them, a number that doubles per level, while the full grid has \(4^d\) cells. In 3D a surface crosses a number of cells that grows like \(4^d\), against \(8^d\) for the full grid. Sparse structures store the surface, not the volume.

Hybrid structures combine the two. Hashed voxel blocks keep a dense array inside each block, which is simple and suits GPUs. The VDB structure hashes blocks and puts a small tree of fixed height inside each, so lookups take constant time and the map still has several resolutions. §5.3.3.4 · pp. 134–135

4. Building point, surfel, and mesh maps

5. Voxel maps in practice

What to estimate. Occupancy has the better recall, so few obstacles are missed, which suits collision avoidance. TSDFs give better surfaces where the world is smooth and lose thin objects (Day 2). A TSDF overestimates distances, which is unsafe for a planner, so systems such as voxblox compute a true ESDF from the TSDF with a wavefront (brushfire) algorithm, and FIESTA computes one from an occupancy map. §5.4.4.1 · p. 138

How to integrate a scan. The measurement integrator applies the sensor model to every voxel the scan observed. There are two designs. §5.4.4.3 · pp. 139–140

IntegratorLoop overNeedsStrength and weakness
Ray tracingBeams: walk each one from the sensor to its end point and update the voxels it crossesOnly the sensor's positionGeneral. But voxels near the sensor are visited by many beams, which repeats work and makes parallel code collide on the same voxel.
ProjectionVoxels: project each one into the sensor and read off the beam that sees itThe full pose and the projection modelEach voxel is written once, so it parallelizes well and dominates on GPUs. Hard to use with unorganized or motion-corrected clouds.

The occupancy widget of Day 1 traces rays. The TSDF widget of Day 2 projects: it visits each cell, computes its bearing from the robot, and looks up the beam with that bearing.

Filling the gap: which voxels does a ray cross?

Ray tracing needs the exact list of cells between two points. Sampling the ray at small steps can skip a cell that the ray only clips. The standard exact method, due to Amanatides and Woo, steps from cell to cell. For a ray \(\mathbf{o} + t\,\mathbf{d}\) with unit direction \(\mathbf{d}\), keep for each axis the ray length \(t\) at which the next cell boundary on that axis is crossed. The smallest of these tells which boundary comes first.

cell = floor(o / Δ)                      # cell that contains the origin
for each axis a:
    step[a]   = sign(d[a])               # +1 or -1: direction of travel
    tMax[a]   = t at the first boundary crossed on axis a
    tDelta[a] = Δ / |d[a]|               # t between two boundaries on axis a
while cell is not the end cell:
    a = axis with the smallest tMax
    cell[a] += step[a]
    tMax[a] += tDelta[a]
    update(cell)

Each loop turn moves to exactly one neighbouring cell with two additions and one comparison per axis, and no cell is skipped or visited twice.

How to scale. Octomap stores occupancy in an octree and merges children whose values agree with their parent, so open space collapses into a few large nodes. It still integrates every beam at the finest resolution, so the update cost stays cubic. Later systems also lower the update resolution with distance, since beams spread out, and skip updates that would change nothing; wavemap does this on a wavelet encoding of the map, which stores differences between resolution levels. §5.4.4.4 · pp. 140–141

Check yourself

Q1. A dense voxel grid takes 32 MB at 10 cm voxels. How much does the same volume take at 2.5 cm?

The voxels are 4 times smaller along each of three axes, so there are 4³ = 64 times as many: 32 MB × 64 = 2048 MB.

Q2. A 2D grid has origin (−10, −10), 0.25 m cells, and 80 cells per row, with index n = i + 80 j. Which array element holds the point (2.6, −3.1)?

i = ⌊12.6 / 0.25⌋ = 50 and j = ⌊6.9 / 0.25⌋ = 27, so n = 50 + 80 × 27 = 2210. Swapping i and j gives 4027; rounding 27.6 up instead of down gives 2290.

Q3. An octree's root octant has an extent of 51.2 m and its finest leaves are 10 cm. How many levels does a lookup descend?

Each level halves the extent: 51.2 / 2⁹ = 0.1 m, so 9 levels. The lookup time grows with this height, which is the cost of a pure tree.

Q4. Why do GPU mapping systems prefer projection-based integration?

Looping over the map gives every voxel exactly one update per scan, with no race conditions and a predictable memory pattern. The price is that it needs the full sensor pose and projection model, which is the opposite of the first option.

Recap

  1. A dense array gives the fastest lookup, \(n = i + N_x(j + N_y k)\), and the largest memory bill: linear in volume, cubic in resolution.
  2. A hash table stores only the blocks that hold data and finds each in constant time. Voxel-block hashing keeps a small dense array in each block.
  3. An octree splits space only where there is data and gives several resolutions, at the cost of a lookup that takes one step per level. Sparse structures grow with the surface area, not the volume.
  4. Point and surfel maps are thinned with grids or trees. Meshes are built directly from points or, more robustly, from an implicit surface.
  5. Ray-tracing integrators loop over beams and need only the sensor position. Projection integrators loop over voxels, need the full sensor model, and parallelize well.
